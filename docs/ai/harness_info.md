# Harness调研与分析

## 一、传统agent的问题

前段时间`openclaw`横空出世，那会各大厂商和自媒体把该工具拥上了神坛，就连春招的时候面试官都得问一下有没有用过龙虾。但就实际体验来说，小龙虾并不稳定，比如他主打的**定时任务**功能。

> 具体症状：第一天调教的好好的，演示效果也让人十分满意——我让他每天早上抓取最新的分布式和后端技术推送给我，他出色的完成了这个过程；但是第二天他似乎忘记了之前演示时候是怎么做的了，尝试了几种方案之后宣告了自己的失败。

当时在我这已经宣告了这个工具的死刑，因为他无法稳定复现之前的链路——我确实可以把每一步都固定下来，但是这又偏离了我一开始用它的初衷：如果我直到确切的每一步怎么做，为什么我不自己写个**定时任务**呢？

这是一个ai**商业化**不得不面对的问题：<u>演示效果良好，但是无法在生产环境可靠运行</u>。

**简单的原因**：假设一个任务的成功执行概率是95%，假如一个任务需要执行10步，这个成功率就是95%的十次方。

harness的意思是马具，我们可以把agent抽象为`llm`+基建，这个基建必须必备约束能力，从而解决上面所说的问题。

Agent Harness 是一个封装 AI 模型并**管理**其生命周期、上下文、工具访问、验证和生产中安全性的**基础设施层**。Harness 决定模型能看见什么、能做什么、何时停止以及当事情出错时会发生什么。

为什么用`harness`去描述呢，因为`llm`就像是一匹马，本身很强大，但是可能会出现没有方向感等问题；我们需要在生产任务中去给这匹马做一定的<u>引导</u>和<u>约束</u>，才能让它帮我们完成目标。



## 二、harness组成

结合`openai`、`claude`等实践，一个成熟的harness包括下面六个部分。

### （一）上下文工程

上下文工程决定了模型执行时每一步能看到哪些信息，包含了系统提示词，检索的文档（rag），历史对话，工具执行结果，当前状态等。上下文工程的**挑战**在于当agent执行了几十轮之后，累积的信息会把有用的上下文推出窗口，我们需要主动管理内容，摘要内容以及清理内容。这个模块要解决的主要问题是保持`llm`的专注。

### （二）工具编排

工具编排管理模型需要明确每一步可用的工具以及如何处理它们的执行，包括**工具选择、参数验证、执行沙箱、超时管理和错误处理**。
 如果只是天真地把一个包含 50 个工具的列表直接交给模型，希望它自动选对工具，这种做法几乎必然失败。

在生产环境中，集成工具通常会根据任务阶段动态调整可用工具。例如：

- **规划阶段**不需要文件系统写入权限
- **代码执行阶段**不需要网络搜索

通过对每一步<u>限制工具集</u>，可以**减少错误发生概率，同时降低 token 消耗**，提升模型执行效率和可靠性。

### （三）状态和内存管理

对于运行时间可能长达数分钟agent系统而言，**持久化**能力必不可少。若agent在任务中途发生崩溃，代理能否从中断处继续执行，而不是被迫从头开始，这直接决定了系统的可用性与稳定性。因此，对于面向生产环境的agent来说，**恢复机制是一项基础要求**。

状态管理不仅涉及单次任务执行过程中的恢复能力，还涵盖**跨会话的记忆管理**。当代理在第二天重新接手某项任务时，它需要明确“记住了什么”、以及“这些记忆是如何被组织和存储的”。如果缺乏合理的记忆结构，代理往往只能依赖重放完整历史上下文，这不仅效率低，也会带来较高的计算与 token 成本。

Anthropic 在这方面采用了一种较为清晰的做法：通过维护一个 `claude-progress.txt` 文件，由代理在执行过程中持续更新，将其作为结构化的临时记录板，并与 Git 历史共同构成任务状态的外部记忆。这样一来，后续会话无需回放全部对话内容，只需读取该文件提供的压缩摘要，即可快速理解先前工作的进展与上下文，从而提升连续执行的效率与稳定性。

### （四）安全

**提前验证**的意思是，在代理输出到达现实世界之前，对其进行检查的一种关键模式。

这是agent工程中影响<u>最大</u>的模式。通过在**每次工具调用后**增加验证步骤，可以检查响应格式、确认输出是否符合预期，并在提交代码前运行测试，从而捕捉那些在多步骤执行中可能累积的“静默失败”。（有点类似快速失败思想）

这一模式的逻辑非常直观：

1. agent生成输出
2. 验证层根据预定义标准评估输出

实践表明，通过引入结构化验证，一些团队的任务完成率从 83% 提升至 96%，而 **模型本身并未改变，改变的是框架**。

### （五）人工介入控制

并非每个代理操作都应完全自主。在生产环境中，**高风险操作**必须经过人工审批，例如删除数据、发送外部通信、执行金融交易或修改基础设施。代理框架需要明确哪些操作需要人工审批，如何发起审批请求，以及代理在等待审批期间的行为等。

挑战在于： **设计审批策略**：

- 审批关卡过多会导致代理执行任务的速度可能低于人工操作
- 审批关卡过少会导致一个错误或幻觉的 API 调用就可能引发生产事故

最佳实践是框架初期采用严格审批要求，随着团队对特定操作类别的信心增加，再逐步放宽审批限制，从而在**安全性与效率之间取得平衡**。

### （六）生命周期管理

**生命周期管理**涵盖代理的启动、健康监控、优雅关闭和崩溃恢复。在生产环境中，代理并非简单的请求-响应功能，而是**长时间运行的进程**，需要与其他生产服务同等的运维关注。

核心实践包括健康检查、资源限制、优雅关闭、崩溃恢复等。缺乏生命周期管理的代理可能成为昂贵、无人监控的进程，并在静默失败中浪费资源与时间。



## 三、实践案例-`OpenHarness`

对照上面说的六个部分，我研究了下`OpenHarness`是怎么实践这六个部分的。

### 1. 上下文工程                                        
 基于代码分析，`OpenHarness` 的上下文工程是一个多层次、自适应的系统。

#### System Prompt组成

<img src="https://imgtu.oss-cn-beijing.aliyuncs.com/blog_img/image-20260408182022854.png" alt="image-20260408182022854" style="zoom:50%;" />

每次对话开始时重新构建，确保最新状态（在实际使用中，感觉得有优化手段比如并行去做装配工作，不然会有明显的阻塞感）。



#### 记忆系统

```python
 def find_relevant_memories(user_prompt: str, cwd: Path) -> list[str]:
      """语义检索相关记忆"""
      memory_dir = cwd / ".claude" / "memory"
      if not memory_dir.exists():
          return []

      # 1. 读取 MEMORY.md 索引
      index = (memory_dir / "MEMORY.md").read_text()
    
      # 2. 提取所有记忆文件路径
      memory_files = _parse_memory_index(index)
    
      # 3. 根据用户提示词做语义匹配
      relevant = []
      for file_path in memory_files:
          content = (memory_dir / file_path).read_text()
          # 简单关键词匹配或更复杂的语义搜索
          if _is_relevant(user_prompt, content):
              relevant.append(content)
    
      return relevant[:5]  # 最多返回 5 个相关记忆
```
这个记忆系统的实现方式本质上是**“索引 + 按需检索 + 上下文注入”**。通过 `MEMORY.md` 作为索引文件，维护所有记忆文件的路径；在每次请求时，根据用户输入对这些记忆内容逐一进行语义匹配（可以是关键词或更复杂的相似度判断），筛选出最相关的少量记忆（最多 5 条）。同时，像 `CLAUDE.md` 这样的全局规则会被固定注入，而其他类型（用户偏好、项目上下文、反馈记录）则按相关性动态加载。最终，这些筛选后的记忆会被拼接进当前上下文，供模型参与推理使用，从而实现“按需记忆、避免上下文膨胀”的效果。

| 类型       | 文件示例               | 何时注入   | 优先级 |
| ---------- | ---------------------- | ---------- | ------ |
| 项目规则   | `CLAUDE.md`            | 每次对话   | 最高   |
| 用户偏好   | `memory/user_*.md`     | 语义相关时 | 高     |
| 项目上下文 | `memory/project_*.md`  | 语义相关时 | 中     |
| 反馈记录   | `memory/feedback_*.md` | 语义相关时 | 中     |

#### 上下文窗口管理与压缩

`OpenHarness` 实现了两级压缩策略：

- `Micro-Compaction`（微压缩）：触发条件是对话历史超过一定长度时，清空旧工具结果的内容，保留调用记录。
- Full Compaction（完全压缩）：触发条件：Micro 压缩后仍超过阈值，调用 LLM 生成结构化摘要

> 有点类似`gc`里面的`Minor GC`和`Full GC`！

##### 完全压缩举例

```python
async def compact_conversation(messages: list[Message], ...) -> list[Message]:
    # 1. 构建压缩提示词
    compact_prompt = (
        BASE_COMPACT_PROMPT
        + """
        请总结以下对话，保留：
        - 技术决策
        - 文件路径
        - 待办任务
        - 错误和解决方案
        """
    )
    # 2. 调用 LLM
    summary = await llm.generate(compact_prompt + conversation_history)
    # 3. 替换旧消息
    return [
        Message(role="assistant", content=f"<summary>{summary}</summary>"),
        *messages[-6:],  # 保留最近 6 条原始消息
    ]
```

#### 对话历史

每次发送对话历史给大模型之前，都要检查是否需要压缩，工具的结果也会被加入对话（可能被微压缩清理）；保留最近的6条上下文保持语义和逻辑的连贯。



### 2. 工具编排                   

#### 工具调用流程

<img src="https://imgtu.oss-cn-beijing.aliyuncs.com/blog_img/image-20260408200001723.png" alt="image-20260408200001723" style="zoom:50%;" />

> 有点像一个简单的审核流。

 LLM 永远只在第1步做决策，其余全由 Harness 控制。

#### 工具定义

每个工具由三个核心组件组成：

```python
class BaseTool(ABC):
    name: str                     # LLM 看到的工具名
    description: str              # LLM 看到的功能说明
    input_model: type[BaseModel]  # 参数定义（Pydantic）

    async def execute(...)        # 实际执行逻辑
    def is_read_only(...)         # 是否只读（影响权限）
    def to_api_schema(...)        # 生成 JSON Schema
```

生成的`json schema`：

```json

{
  "name": "bash",
  "description": "Run a shell command in the local repository.",
  "input_schema": {
    "type": "object",
    "properties": {
      "command": {
        "type": "string",
        "description": "Shell command to execute"
      },
      "cwd": {
        "type": "string",
        "description": "Working directory override"
      },
      "timeout_seconds": {
        "type": "integer",
        "default": 120,
        "minimum": 1,
        "maximum": 600
      }
    },
    "required": ["command"]
  }
}
```

LLM 从来不知道工具的实现细节，它只看到这个 JSON Schema。这就是 **Harness** 的意义：**LLM 负责决策，Harness 负责执行**。

#### 持久化分层

##### 会话快照

问题：若 agent 在任务中途发生崩溃，代理能否从中断处继续执行。

`OpenHarness` 的做法是：**每次对话轮次结束后自动保存完整快照**。

写入逻辑（双文件策略）
```python
# 同时写两个文件
latest_path.write_text(data)              # latest.json → 快速恢复
session_path.write_text(data)             # session-{id}.json → 历史记录
```

**`latest.json`**：始终保存“当前最新会话状态”，用于 **快速恢复（crash recovery）**

**`session-{id}.json`**：每次生成一个新文件，用于 **完整历史记录追踪**

磁盘文件：

```txt
~/.openharness/data/sessions/
└── OpenHarness-f13922633a96/       ← 按项目隔离
    ├── latest.json                  ← 最新会话（快速恢复用）
    ├── session-1054355182ba.json    ← 历史会话 1
    ├── session-520b85951d1e.json    ← 历史会话 2
    └── session-c90047fbbc92.json    ← 历史会话 3
```

##### 持久记忆

当代理在第二天重新接手某项任务时，它需要明确两件事：

1. 记住了什么
2. 这些记忆是如何被组织和存储的

###### 完整架构

```text
~/.openharness/data/memory/
└── MyProject-a1b2c3d4e5f6/
    ├── MEMORY.md                 ← 索引文件
    ├── api_design.md             ← 记忆：API 设计决策
    ├── user_preferences.md       ← 记忆：用户偏好
    └── debugging_history.md      ← 记忆：排错经验
```

每个项目独立拥有自己的记忆目录，既方便程序检索，也方便人工维护。

**记忆生成**：每新来一条记忆，先给它生成文件名，存成一个 markdown 文件，然后把这条文件链接补到 `MEMORY.md` 里。

###### 索引和具体记忆

在这个记忆系统里，`MEMORY.md` 充当的是一个总索引的角色，可以把它理解成整个记忆库的目录页。

```md
# Memory Index
- [API 设计决策](api_design.md)
- [用户偏好](user_preferences.md)
- [调试历史](debugging_history.md)
```

代理启动之后，不需要先逐个扫描所有记忆文件，而是先读取这个索引文件，就能快速知道当前项目里已经沉淀了哪些长期记忆，比如 API 设计决策、用户偏好、调试历史等。

**好处**：

1. 模型在构造上下文时可以先整体掌握“现在有哪些知识可用”；
2. 人也可以通过这份索引很直观地检查当前记忆覆盖了哪些主题，便于维护；

具体到每一条记忆，系统采用的是 **YAML Frontmatter + Markdown 正文** 的组织方式。

```md
---
name: API 设计决策
description: RESTful API 的设计原则和约定
type: technical
---
```

每个记忆文件的开头先用一段 YAML 记录结构化元数据，比如记忆名称、记忆说明以及类型；这些字段主要服务于程序侧的处理，比如后续做检索、分类、排序，或者让模型在读取之前先快速理解这条记忆的大致主题。

紧接着在元数据下面，才是 Markdown 格式的正文内容，用来记录真正的长期知识，例如规则约定、历史决策、用户偏好或者调试经验等。

这样的设计其实兼顾了两种需求：<u>结构化</u>和<u>自由化</u>。

###### 记忆检索

用户提问时，系统首先会对用户输入进行分词处理，将一句自然语言拆解成多个 token。例如，对于“API设计”这样的输入，会被拆分为 `{"api", "设", "计"}`。

系统不会直接读取所有完整内容，而是先扫描最多 100 个记忆文件的“头部信息”，包括：

| 字段         | 含义     |
| ------------ | -------- |
| title        | 记忆标题 |
| description  | 记忆描述 |
| body_preview | 正文预览 |
| modified_at  | 修改时间 |

这样可以在保证效率的前提下完成初步筛选。

对于每个记忆文件，系统会分别在两部分中进行关键词匹配：

| 匹配区域 | 内容        | 作用             |
| -------- | ----------- | ---------------- |
| meta     | 标题 + 描述 | 表示“主题相关性” |
| body     | 正文预览    | 表示“内容相关性” |

对应代码：

```
meta_hits = sum(1 for t in tokens if t in meta)
body_hits = sum(1 for t in tokens if t in body)
```

接下来，系统会采用一个简单但有效的加权公式：

```
score = meta_hits * 2.0 + body_hits
```

其核心规则如下：

| 命中类型   | 权重 | 含义               |
| ---------- | ---- | ------------------ |
| 元数据命中 | ×2   | 更重要（主题匹配） |
| 正文命中   | ×1   | 次要（内容补充）   |

之后系统会返回分数top-k的记忆作为prompt的一部分。
