## 事务
用户的一系列数据库操作不可分割，要么全执行，要么全不执行。
事务具有 ACID 特性。
### ACID 特性
- 原子性：事务不可分割，要么全提交成功，要么回滚
- 一致性：数据库的一致性以及业务上的一致性
- 隔离性：事务之间互不影响
	- 四大隔离级别：读未提交，读已提交，可重复度，串行化
- 持久性：事务被提交后，数据库里面的变更是持久的

## XA 两阶段提交协议
是资源管理器和事务协调器的接口标准，用来管理分布式事务，可以保证数据的**强一致性**，可以解决临时性的系统性故障（进程，网络节点，通信等），主要是为了保证事务的一致性，步步操作都是为了记日志，在系统故障的时候有较强恢复能力。

### 执行过程
两阶段提交协议分为两个阶段（这句话没有语病）：
阶段一：
（1）：事务协调器通知所有资源管理器准备事务。
（2）：资源管理器写事务日志，并执行事务，但是不提交，将就绪状态返回给事务协调器。
阶段二：
（1）：事务协调器根据资管管理器的消息决定是否提交或取消（回滚），并通知资源管理器
（2）：各个资源管理器执行命令并返回结果。

### 缺点
- 同步阻塞
- 单点故障（主要指的是事务协调器宕机后果严重）
- 数据不一致：二阶段如果出现网络波动，会导致部分资源管理器提交
- 状态不确定：某事务协调器跟进完某个事务后宕机，如果对接的也同时宕机，即使恢复，这条事务的状态也无从考究


## 分布式理论
分布式系统一致性是计算机系统的难题，比如数据复制场景：对某个副本进行更新的同时，也必须更新其他的副本，这个问题需要同时考虑一致性和性能的问题。
### cap 理论
一个系统不可能同时满足一致性，可用性，分区容错性。但是由于是分布式系统，所以分区容错性是必须要保证的。一般我们需要在一致性和可用性之间进行权衡。
- CP：一致性&分区容错性，追求数据的**强一致性**，弱化可用性。一般用于对数据要求较高的场景，比如金融。但是性能较低，代表有 XA，Seata AT 的读已提交。
- AP：可用性&分区容错性，追求数据**最终一致**即可。这种模式性能高，能满足高并发的需求，常见的有 TCC，基于消息的最终一致性，saga 等。
### BASE 理论
Base 理论：基本可用+软状态+最终一致性，是对 cap 的一致性和可用性的权衡，核心思想：用最终一致性获取可用性。
- 基本可用：系统在出现故障时，仍然能够对外提供服务，但可能会降级或部分不可用
- 软状态：系统允许存在中间状态，这些状态可能在一段时间内不一致
- 最终一致性：系统在经过一段时间后，数据最终会达到一致状态

## TCC 柔性事务
核心思想：把一个大事务拆成三个可控阶段（Try / Confirm / Cancel），由业务自己保证最终一致性。
>  TCC 在电商金融落地比较多。


TCC 是对两阶段提交的一种改进，对业务的侵入性大。
三阶段：
- `try`：完成业务准备
- `confirm`：完成业务提交
- `cancel`：完成事务的回滚

详细过程：

<img src="https://imgtu.oss-cn-beijing.aliyuncs.com/blog_img/image-20260330095704340.png" alt="image-20260330095704340" style="zoom: 67%;" />
1. 业务应用向事务协调器发起事务请求
2. 业务应用调用所有服务的 try 接口，完成一阶段
3. 业务应用根据 try 接口的结果，决定是 confirm 还是 cancel，并发请求给**事务协调器**
4. 事务协调器进行执行

不足：
1. 对应用侵入性强，每个分支都得实现三阶段，改造成本高
2. 实现难度大，需要根据网络状态等实现不同的回滚策略，为了满足一致性的需求，confirm 和 cancel 都必须冥等。

## 基于消息的最终一致性
普通的消息处理流程如下，若生产消息和消费消息都是数据库事务，则不能保证生产和消费的事务同时成功或同时失败。
<img src="https://imgtu.oss-cn-beijing.aliyuncs.com/blog_img/image-20260330100513405.png" alt="image-20260330100513405" style="zoom:50%;" />
解决方案：
在对数据一致性要求较高的场景，经常采用基于消息的一致性方案，通过消息中间件保证上下游的数据一致性。
<img src="https://imgtu.oss-cn-beijing.aliyuncs.com/blog_img/image-20260330100737013.png" alt="image-20260330100737013" style="zoom:67%;" />
主要流程：
1. 生产消息时，记录消息到数据库，状态为待发送，且**消息数据和业务数据捆绑在一个事务**。
2. 消息记录完成之后，用一个定时任务去投递待发送的消息。
3. 如果投递失败就重试，直到消息队列 ack；再将状态标记为已发送。
4. 如果下游消费失败，也进行重试。

缺点：对应用侵入性高，需要大量业务改造。
