### TCC 简介
TCC 模式指的是把自定义的分支事务纳入分布式事务的管理，相较于 XA，TCC 不依赖 RM 对 XA 的支持，而是通过业务逻辑调度来实现分布式事务。
#### 和 AT 对比
`seata` 分布式事务整体上是一个**两阶段提交**模型。全局事务由若干个分支事务组成，需要满足两阶段提交的要求，需要每个分支事务具备下面的行为：
1. 一阶段 `Prepare`
2. 二阶段 `Commit` 或 rollback
AT 和 TCC 都遵循，但是最大的差别在于是**自动实现**还是**自定义**这个三个行为。
##### AT
依赖数据库的本地事务能力。
• 一阶段 prepare：Seata 框架自动完成准备（在一个本地事务内完成）。
• 二阶段 commit：Seata 框架自动清理事务日志。
• 二阶段 rollback：Seata 框架自动完成数据回滚（在一个本地事务内完成）。

##### TCC
不强依赖关系型数据库的本地事务能力。
• 一阶段 prepare：调用自定义的 prepare 逻辑。
• 二阶段 commit：调用自定义的 commit 逻辑。
• 二阶段 rollback：调用自定义的 rollback 逻辑。

| 对比维度  | AT 模式                                   | TCC 模式                                         |
| ----- | --------------------------------------- | ---------------------------------------------- |
| 依赖条件  | 强依赖关系型数据库的本地事务能力                        | 不强依赖关系型数据库，支持异构业务资源                            |
| 资源定义  | 将每个关系型数据库作为分布式事务资源                      | 将每组自定义 TCC 服务接口作为分布式事务资源                       |
| 一阶段操作 | 拦截 JDBC 请求，在本地事务内完成业务操作+事务日志写入，自动注册分支事务 | 拦截 TCC 服务的 try () 方法调用，注册分支事务后执行自定义资源预留/规则校验逻辑 |
| 二阶段提交 | 框架自动删除对应分支事务的事务日志，无业务侵入                 | 调用自定义 TCC 服务的 confirm () 方法，完成资源正式提交           |
| 二阶段回滚 | 框架自动根据事务日志构建回滚语句，完成数据回滚                 | 调用自定义 TCC 服务的 cancel () 方法，回滚 try 阶段的资源预留      |
| 业务侵入性 | 零业务侵入，完全由 Seata 框架自动处理                  | 高侵入性，需实现 Try/Confirm/Cancel 三组业务接口             |

### 如何设计 TCC 模式
在接入 TCC 模式时，用户的重点工作就是定义 TCC服务接口和实现 TCC接口上。TCC 的业务实现，需要根据具体业务场景做针对性的处理。
TCC 认为业务系统中的某业务逻辑，对外服务有不确定性，对其尝试是临时操作，需要保留可取消性。
常见的两种 TCC 实现模式有**资源预留模式**和**补偿模式**。
#### 资源预留模式
一阶段预留资源，确保二阶段能执行下去。
**举例：支付场景**
（1）一阶段把要支付的金额从账户里面预留出来，别的分布式事务就用不了这部分被冻结的金额了。
（2）二阶段如果要提交，就扣掉这部分金额。
（3）二阶段如果要回滚，就取消冻结的金额。

#### 补偿模式
实际场景里面，补偿模式用的比较多，比如下单减库存。
**举例：减库存**
（1）一阶段减少库存，记录库存减少的数量。
（2）二阶段如果要提交，删除额外记录的信息。
（3）二阶段如果要回滚，根据记录的信息，把库存数量加回去。

> 两种模式的三阶段都需要考虑冥等性。
